The ticket flow

How one tracked issue becomes merged history, and which skill owns each step.

Most work in this pack runs through one path. It is worth reading once end to end, because every skill on it assumes you know where it sits.

Why a driver, not a checklist

A ticket has a lifecycle, and a lifecycle is exactly the thing a conversation loses. ticket owns four verbs, and each one ends with state written somewhere that survives the session: a locked brief on the issue, a branch, a review round on the pull request, a close-out.

The four verbs

triage reads the issue cold and decides whether it is ready. Thin scope goes to scope; work too large for one context is sliced by orchestrate. What comes out is a work order precise enough to hand to an agent who was not in the room.

start executes that work order on its own branch, in its own worktree.

revise actions a review round. code-review supplies the findings, one verdict per enumerated item, so the round terminates instead of sprawling.

finalize closes out a merged ticket: the ledger row, the archive, the follow-ups that are real and the ones that were only anxiety.

Where the other skills come in

The flow above is the common path, not the only one. plan-review is worth a round whenever the work order is load-bearing. pr-body writes and scores the description before the pull request opens, because a body written after the fact describes the diff instead of the change.
