# Epic rework spec

Rework the planning stack: wayfinder becomes the epic driver, tickets follow an
epic / spike / build taxonomy, daemon-era assumptions get purged, and
agent-performance feedback accumulates locally between manual calibration
passes. This rework is itself the first epic (see Sequencing).

## Settled decisions

* Wayfinder evolves in place into the epic driver; no parallel skill.
* The epic's source of truth is checked-in OpenSpec markdown in the target
  repo. Trunk-based: `proposal.md` and `design.md` land on main early, via a
  small ordinary PR, when the epic opens; only `ledger.md` rides a standing
  draft PR merged at close-out. The GitHub epic issue tracks children and
  links the spec at its main path; its body is never authoritative.
* A spec amendment discovered at triage is its own docs-only PR to main,
  merged before the work order is stamped. Build PRs never touch `openspec/`.
* Type labels reset to a single taxonomy plus one state label (`deferred`);
  `wayfinder:*` labels retire. Migration is a script run across an
  operator-approved repo list generated by a spike, not prose.
* agentflow is retired as a process. Every ticket runs with a human in the
  loop; daemon-era language is retired by a standing pattern gate, not a
  one-time grep.
* Feedback has two streams: model rows (new store, feed orchestrate's routing
  table as provisional field observations) and slicing rows (the telemetry
  `ticket.py record` already writes — verified live, rows through 2026-08-24).
  Rubric and table edits happen only when a human runs `/calibrate`. Finalize
  never commits, opens PRs, or drafts amendments.
* One combined assessment covers both streams, nudged after 5 finished tickets
  since the last assessment marker.
* The epic session is the operator's home session and stays ledger-light;
  builds, triage, and interview spikes run as fresh attended sessions, and
  coordinators never nest. Child epics are out of scope for this first epic.
* Triage keeps ownership of slicing and the stamped order. Promotion to an
  epic is conjunctive: more than four chunks AND at least one unsettled
  decision. Purely mechanical oversize is split by hand into serial build
  tickets instead — the epic apparatus is for fog, not for bulk.
* Wayfinder's candidate-disposition protocol is superseded, not ported (see
  Superseded protocol).

## Out of scope

* `docs/evidence/contract-v2.json` and everything `scripts/validate.py` pins by
  SHA-256 to the agentflow repo: untouched. Unpinning is agentflow-side work,
  tracked there if ever.
* `docs/evidence/envelope-v2.md` keeps its `Wayfinder` rows deliberately: they
  are the pinned evidence contract's vocabulary, shared with the upstream
  fixture, and renaming them is agentflow-side work. The stale skill name
  there is known and accepted.
* The vendored trees `.claude/skills/` and `.agents/skills/`: never edited
  directly; they follow the source through the normal pin bump.
* `ticket:*` status labels: a separate axis the tracker binding depends on
  (`bindings/github-issues.md`); the label migration does not create, rename,
  or delete them.
* Historical docs under `docs/scope/` and example fixtures under
  `docs/evidence/examples/`: untouched.

## Taxonomy

* Three type labels — `epic`, `spike`, `build` — plus the `deferred` state
  label this plan adds. (The `ticket:*` status axis is separate, pre-existing,
  and out of scope; this taxonomy does not claim to be the only labels.)
* An epic is the container: one OpenSpec change, one GitHub issue with native
  child issues, one epic ledger.
* A spike answers a question and closes with a resolution comment. Flavors:
  research, interview, mockup, and human prerequisite (work only the operator
  can do that unblocks a decision).
* A build ticket is implementable work driven through `/ticket`.
* `deferred` marks a child of an epic issue as outside that epic's current
  scope: a deferred follow-up is filed as a native child of the epic that
  surfaced it, carrying the label. It is not blocking: blocked-in-scope work
  uses GitHub's native `blocked-by` relationship and self-clears; `deferred`
  never self-clears — it waits for a human disposition at that epic's
  close-out, and every disposition moves the label, so the completion gate is
  one `gh` query.
* Type-label migration: `wayfinder:map` → `epic`; research / prototype /
  interview / task tickets → `spike` (a `wayfinder:task` is by its own
  definition never an execution errand); existing build issues → `build`. The
  state labels are handled under Superseded protocol.

## Epic driver (wayfinder evolved)

* Rename `skills/drivers/wayfinder` → `skills/drivers/epic`, invoked as `/epic`.
* The rename edit set — paths and literal identifiers only; every instruction
  or description rewrite belongs to the behavior child:
  * `scripts/validate.py` `EXPECTED` entry `drivers/wayfinder`.
  * `skills/drivers/epic/agents/openai.yaml` (validator requires one per skill).
  * `.github/workflows/validate.yml` post-install assertion list.
  * `README.md` skill table row and any prose references.
  * `skills/workflows/scope/SKILL.md` routing (`wayfinder` → `epic`, every
    occurrence) plus the routing row's note that `/epic` subsumes the scope
    ledger for epic-routed work.
  * `references/github-tracker.md`: renamed with the skill (path only; its
    content rewrite is the behavior child's).
  * `tests/test_behavior.py` pins: dispositioned per Superseded protocol —
    pins asserting candidate/disposition/state-label content are deleted; pins
    asserting native structure and label bootstrap are rewritten against the
    new page; never left referencing the old name.
  * `skills/drivers/ticket/references/slicing.md`: the more-than-four-chunks
    sentence gains the `/epic` promotion pointer.
  * dotfiles `PUBLISHED_SKILLS` (outside this repo): an explicit operator gate
    — rerun `install.sh` after the rename merges and before any later child
    starts, or `~/.claude/skills/wayfinder` dangles and `/epic` is not
    installed.
  * agentflow pins (outside this repo): before the rename merges, the operator
    verifies nothing in `agentflow/capabilities.toml` or `skills-lock.json`
    pins a `drivers/wayfinder` path; a hit is agentflow-side work that must
    land first.
* An epic lives at `openspec/changes/<epic-slug>/` in the target repo:
  * `proposal.md` — destination, scope boundary, and the epic-level risk
    contract. At stamping time, triage copies the relevant risk lines from it
    into the child's work order; the stamped work order is what governs that
    child (satisfying scope's rule that the risk contract lives in the
    authoritative artifact), and a later `proposal.md` amendment never
    retroactively changes an already-stamped order.
  * `design.md` — ADRs only where the charter's ADR-home rule lands them in
    OpenSpec; in a repo with an established `docs/adr/` tree (this one), ADRs
    go there and `design.md` holds the destination rationale.
  * `ledger.md` — the epic ledger, below.
* Repos without OpenSpec get `/openspec-adopt` first, as its own
  documentation-only PR — its rule forbids bundling adoption with a change.
* Triage as you go: file spikes and build tickets when their prerequisites
  settle. A build ticket's filing cites the Fog lines (the ledger's `## Fog`
  section, below) standing at filing time; it is filed only when no open
  spike and no standing Fog line can invalidate it — and Fog lines leave the
  ledger only via a `Decisions` line or a spike, never by silent deletion —
  plus every load-bearing ruling it depends on is recorded as an
  ADR, and — for a user-facing surface — its `/ui-craft` spec is locked (the
  mockup spike produces the lock before the dependent build is filed).
* A change to the destination is a `Decisions` line plus an ADR, never a
  silent planning commit.
* On epic completion, the close-out PR (the standing ledger PR) also carries
  the archive move for the OpenSpec change, committed before the PR leaves
  draft — matching openspec-adopt's archive-in-the-finishing-PR rule.

### The epic ledger

`ledger.md` — always "the epic ledger" in the epic skill's own prose and in
`slicing.md`'s pointer; the pack carries several other qualified ledgers and
this one stays out of their lists — is the resumable state and a pinned interface: the home
session writes it, the status renderer reads it. The grammar is per section:
`Spikes` and `Builds` lines carry a state token — the split point is the
first ` — ` whose following field matches that section's closed token set,
and any free text sits behind a second ` — `; in `Builds`, a merged-pending
PR is the state token itself (`pr:#<n>`). `Decisions` and `Deferred` lines
carry only free text after the first ` — `. `Rounds` lines lead with the
date, then the issue reference, then free text. `Notes` and `Fog` are plain
lines. Ledger titles never contain ` — ` (use a plain hyphen). Prose beyond
one line lives in the ticket. The template is normative:

```markdown
# Ledger — <epic title>

## Status
next: <the single next action, one line>
updated: <YYYY-MM-DD>

## Notes
- <pointer only: a skill to invoke, or the location of an existing rule>

## Fog
- <something not yet precise enough to ticket>

## Decisions
- #<n> <title> — <one-line gist of the resolved spike's ruling>

## Spikes
- #<n> <title> — open | dispatched | resolved — <one-line gist>

## Builds
- #<n> <title> — filed | triaged | in-progress | pr:#<n> | merged

## Deferred
- #<n> <title> — <one-line reason it can wait>

## Rounds
- <YYYY-MM-DD> #<n> — <agents used, outcome, one line>
```

* `Notes` holds pointers, never rules: anything that would read as a new
  standing instruction goes to an ADR instead.
* `Decisions` is derived: one line per resolved spike whose ruling stands.
* The home session is the epic ledger's only writer; the renderer is its only
  other reader. Build and triage sessions report through ticket comments and
  the PR; the home session syncs the ledger from the tickets on return.
* Live tracker state wins over the ledger everywhere: the ledger is the index,
  `gh` is the truth — including `Deferred`, whose truth side is the `deferred`
  label.
* The ledger ships through one standing draft PR per epic, in a dedicated
  planning worktree. Commits are signed-off (`-s` — DCO is unfixable after the
  fact) and pushed as the home session goes; the branch takes a merge from
  main only when it actually needs one (conflicts are impossible by
  construction — nothing else touches the change directory). Close-out merges
  it, with the archive move; then the planning worktree is torn down as an
  explicit close-out step.
* Build worktrees branch from main and read `proposal.md`/`design.md` there
  like any other file; work orders live in ticket comments.
* Epic completion gate, all tracker-checkable and emitted pass/fail by the
  renderer: no open spike, every build merged, and no open child of this epic
  carrying `deferred`. Fog is the operator's own prompt before calling it
  done, not part of the gate.

### Status renderer

* A stdlib Python script in the epic skill (`scripts/epic_status.py`) parses
  the epic ledger plus `gh` issue and PR states and emits a Mermaid diagram
  and a one-screen text summary. No agent in the loop; same inputs, same
  picture.
* Where ledger and tracker disagree, the renderer shows tracker state and
  marks the ledger line stale — the home session's cue to sync.
* The renderer also evaluates the epic completion gate from `gh` alone and
  prints it as three pass/fail lines, so close-out is a read, not a judgment.

### Session topology

* The epic session is the operator's home session. It stays at ledger
  altitude: it files issues, updates the epic ledger, and dispatches work. It
  never reads the repo deeply and never coordinates chunks — context stays
  light by design, not by compaction.
* Each build runs as a fresh attended session (`/ticket start`), rehydrating
  from the work-order comment. On a chunked order that session coordinates per
  the existing coordinator-mode reference, with the operator sitting with it.
* Triage runs as a fresh session per ticket. For an epic child it writes no
  spec documents to any branch — the work order is its artifact, and a needed
  spec amendment ships as a docs-only PR to main before the order is stamped
  (`skills/drivers/ticket/SKILL.md`'s triage line is amended to say so).
* Research-only spikes dispatch as background sub-agents from the home
  session. The home session verifies the findings comment exists before
  marking the spike resolved; a spike whose worker died stays `dispatched`.
  This replaces wayfinder's worker-supervision rule — with claim labels gone,
  verifying the findings comment is the whole obligation. Interview and
  mockup spikes run as fresh attended sessions.
* Coordinators never nest. Independent builds run in parallel, each in its own
  session and worktree; the epic ledger tracks them all, and the only
  serialization is the operator's attention.

### Follow-ups and orphan control

* These rules bind sessions working under an epic — the work order names its
  epic, which is how a fresh build session knows they apply; outside an epic,
  `review-actions.md`'s follow-up rule stands unchanged. (`review-actions.md`
  itself gains the one-line under-an-epic labeling clause, in the behavior
  child's edit set, so the session that files reads the rule where it works.)
* A follow-up joins the epic only if the epic's destination (per
  `proposal.md`) cannot be reached without it; it becomes a child issue and
  enters the normal triage flow.
* Any other follow-up — including `review-actions.md`'s "necessary follow-up"
  filed from a build session — is filed as a child of the epic issue with a
  type label plus `deferred`, and the issue number is reported on the ticket.
  The home session's sync turns it into a ledger `Deferred` line; the labeled
  child, not the ledger, is the record.
* Epic close-out sweeps this epic's `deferred` children via `gh`: each gets a
  human disposition, and every disposition moves the label — promote to its
  own spike or build (label off; if promoted at close-out it files outside
  the closing epic), re-park under a future epic (reparented, label stays,
  no longer this epic's child), or close as won't-do (closed, label off).
  The gate is the query: the epic does not archive while an open child
  carries `deferred`.
* First entry for this epic's Deferred list: docs-only auto-merge CI — merge a
  PR touching only docs paths when filed by a code owner (`CODEOWNERS` check
  plus `gh pr merge --auto` behind a paths filter). A follow-up, not a child.

## Superseded protocol

Wayfinder's candidate-disposition machinery is replaced by ledger
triage-as-you-go, element by element:

* `wayfinder:awaiting-disposition` (durable state) and `wayfinder:resolving`
  (claim label): deleted. Incremental triage replaces batch disposition, and a
  human-attended session needs no claim label. The migration script lists
  every issue carrying either label for human disposition before deleting the
  labels; it never deletes state it hasn't surfaced.
* `wayfinder_findings:` blocks, `Wayfinder candidate:` markers, and candidate
  replay identity: superseded by the `deferred` label and the close-out sweep.
  Markers on already-filed issues become inert prose; no rewrite of old
  issues is attempted.
* `Wayfinder handoff: #<map>` markers: superseded by native child-issue
  relationships; also inert prose.
* The three-fact handoff triad: superseded by the work-order comment.
* The four handoff gates: two survive verbatim in the filing rule (ADRs
  recorded; `/ui-craft` lock for user-facing surfaces); two are superseded
  (fog check → the Fog section; disposition check → the `deferred` sweep).
* The protocol pins in `tests/test_behavior.py`
  (`WayfinderResearchDispatchHandshakeTests`, 18 tests): protocol pins deleted
  with the protocol; the two `/research` pins —
  `test_research_recognizes_it_is_already_running_in_a_worker` and
  `test_research_forbids_recursive_delegation` — move to a retained class;
  tracker pins split per the rename edit set. New pins land for the ledger
  template, the deferred filing rule, and dispatched-spike verification.

## Coordinator and daemon purge

* Triage still owns slicing and the stamp (`Execution:`, per-chunk `Agent:`,
  `Open as:`); start still refuses rather than re-slices. No contract change.
* Chunks are never issues: a sliced ticket keeps its chunks as sub-orders in
  the work-order comment, one coordinator, one branch, one PR. More than four
  chunks means the ticket is really an epic — the existing countable rule, now
  pointing at `/epic`.
* `coordinator-mode.md` stays where it is — it delegates to orchestrate's
  rules and adds only ticket-specific machinery.
* The purge is a standing pattern gate, not a one-time grep: a new check in
  `scripts/validate.py` keyed on (term, path-glob allowlist) — the existing
  `FORBIDDEN` tuple has no path dimension, so this is its own loop — scanning
  tracked files under `skills/` only. That scope keeps this spec, `AGENTS.md`,
  `profile/`, `docs/`, and `tests/` out of the gate's reach by construction.
* The term list, in the spec so the gate is falsifiable: `agentflow`,
  `daemon`, `unattended`. Broad words that also appear in legitimate prose
  (`fleet`, `AFK`, `autonomously`) are deliberately not terms.
* Purge targets, enumerated — only files with live hits: ui-craft's two
  "Headless (AgentFlow)" mode branches (they contradict human-in-the-loop and
  are deleted as behavior, not reworded), ui-craft's `revise.md` "never an
  unattended phase" sentence (reworded in place — it asserts the right thing
  in a banned word), and implement's BUILD_PROMPT rationale comment. Ticket,
  scope, and orchestrate prose carry no gate terms today; the gate's job
  there is to keep them clean, not to clean them. The epic skill's own pages
  (which inherit wayfinder's `unattended` lines) are cleaned by the behavior
  child, whose done condition includes "no gate terms in `skills/drivers/epic/`".
* Allowlist, written into the gate and keyed (term, path, line-substring) so
  an exemption is no wider than its occurrence: orchestrate's benchmark
  provenance (`references/routing-table.md` header, `references/benchmark/`),
  cbm-onboard's daemon endpoint and `.agentflow/` ignore string, orchestrate's
  "daemon restarts" example. Matching is case-insensitive.
* Acceptance: the term list above is in the gate, each enumerated target is
  shown red before its edit and green after, and the gate passes on the final
  tree.

## Feedback and calibration

* Slicing stream: `~/.config/ticket/telemetry.jsonl`, exactly as `ticket.py
  record` writes it today (verdict, role-tagged peaks, chunks, traits, repo).
  Nothing new is written for it; `record` stays the single writer. A `no-data`
  verdict appends nothing, which is correct — it carries nothing to calibrate.
* Model stream: `~/.config/agent-calibration/models.jsonl`, append-only. A
  chunked finalize stages one row per chunk via a new `ticket.py stage`
  subcommand taking bounded flags only — ticket id, repo, model id, chunk
  index, outcome from the closed enum `verified | failed-verification |
  not-verified`, and counts of blocking and not-blocking review findings
  (the pack's existing split; no severity scale exists and none is invented)
  — matching the store's never-prose invariant. Ticket id and repo make a
  3-row threshold auditable back to the work it describes. Review-finding
  prose stays on the ticket, where `/calibrate` pulls from at assessment
  time; fields overlapping telemetry are never restated.
* Assessment markers: `~/.config/agent-calibration/assessments.jsonl`, one row
  per `/calibrate` run. The nudge unit is recorded tickets (a `no-data`
  verdict never wrote a telemetry row and never counts): `ticket.py rounds`
  counts telemetry rows newer than the last marker, and on first run — no
  marker file — seeds a marker instead of counting the store's whole history.
* `ticket.py` is the single owner of all three calibration files: `stage`,
  `rounds`, the first-run seed, and a marker-append subcommand all live
  there. `/calibrate`'s script reads the stores and appends its marker and
  archive copies only by calling `ticket.py` — one schema home, no second
  writer. Both new subcommands
  inherit `ticket.py`'s failure semantics — a denied write is a visible
  one-line report naming the path and the fix, never a blocked verb.
* At 5 or more finished tickets since the last marker, finalize ends with one
  nudge line: "N tickets since the last calibration assessment; run
  /calibrate when ready."
* Finalize's misprediction path — drafting a `slicing.md` amendment and
  showing it to the user — moves to `/calibrate`; finalize reports the verdict
  line only. No prose dump, no commits, no epic-ledger writes.
* `/calibrate` is the manual reassess step, a small standalone skill:
  1. Read the telemetry and model stores since the last marker.
  2. Propose edits, each needing 3+ supporting rows: the routing table
     (`skills/drivers/orchestrate/references/routing-table.md`) for model
     trends — field observations land in a dated provisional section, never
     in the stamped rows, which change only via a benchmark replay per
     `references/benchmark/README.md` — and each run also dispositions the
     standing provisional entries (promote via replay, restate, or drop), so
     the section turns over rather than accreting; `slicing.md` for task-shape trends —
     its prose and the constants in `ticket.py` (`DEGRADE_PEAK`, `FLOOR_PEAK`)
     move together or they drift.
  3. Anchor-row prose the stores don't carry (Work description, Right-shape
     call) is pulled from the linked tickets via `gh` at assessment time.
  4. Human reviews; approved edits land through the normal PR flow.
  5. Append the assessment marker; archive consumed model rows by copying to
     `~/.config/agent-calibration/archive/<date>-models.jsonl` — live files
     stay append-only. All through the skill's own script.

## Label migration

* A spike generates the inputs before the script is written: the target-repo
  list (`gh repo list`, pasted and operator-approved in the resolution) and
  the label inventory (`gh label list` across that list), with a disposition
  for every label (create / relabel / delete / out of scope). Prose never
  enumerates what the inventory can.
* The migration script is a throwaway: stdlib Python driving `gh`, written at
  execution time into the session scratch directory, never committed anywhere.
  Dry-run by default; `--apply` to execute; idempotent. Its preflight aborts
  unless the installed skill copy is the new one (`~/.claude/skills/epic`
  present, `~/.claude/skills/wayfinder` absent) — the ordering dependency
  enforced as a refusal, not remembered. Before deleting a state label it
  prints the issues carrying it and requires explicit acknowledgment.
* The apply gate has a literal stamp: the spike resolution carries the repo
  list in a fenced block headed `Approved repo list:`, and `--apply` is run
  only against a list read from that block. No block, no apply. The durable record is the ticket: the spike's approved
  inventory, the dry-run output, and the apply log, attached as comments.
* Acceptance, quantified over the spike's approved repo list: dry-run output
  matches the inventory's disposition column on every listed repo; post-apply,
  `gh label list` shows the four new labels and no `wayfinder:*` labels on any
  listed repo.
* The apply runs only after the behavior child has merged AND the dotfiles
  reinstall has run: label recreation comes from the operator's installed
  copy, which creates six labels at bootstrap plus `wayfinder:resolving` on
  demand mid-protocol — seven creation sites that survive a purely mechanical
  rename. Deleting labels while any installed copy still recreates them
  reopens the window.

## Sequencing — the first epic

This rework runs as its own epic in this repo, bootstrapped by hand from this
spec since the epic skill doesn't exist yet. Children, in dependency order:

   Then the epic opens: epic issue, `openspec/changes/epic-rework/` with the
   proposal (this document plus the epic-level risk contract it currently
   lacks, landed on main via a small PR), epic ledger on the standing draft
   PR, maintained by hand to the template above. Done when the adoption PR
   and the proposal PR are merged, the epic issue exists with the `epic`
   label, and the draft ledger PR is open.

   operator-approved in the resolution comment.
2. Build: mechanical rename `wayfinder` → `epic` — paths, `EXPECTED`, CI
   install list, README, scope routing, link fixes, test renames. Per
   ADR-51's own precedent the move lands alone: no instruction changes in
   this diff. Done when validate, the full suite, and the post-install check
   pass on the renamed tree.

   (promotion is unavailable mid-bootstrap, and unnecessary — this is the
   mechanical-oversize case the conjunctive rule sends to a hand split):
   * 3a — epic skill content: ledger template and planning-PR workflow

## Risk contract

- **Must prevent:** secret exposure; irreversible loss of authoritative data —
  in this epic, tracker state: no label carrying claim or disposition state is
  deleted without its issues surfaced and acknowledged first; silent incorrect
  success — a calibration row or telemetry record that misattributes work;
  breaking agentflow's per-file pins unknowingly (the pin check gate runs
  before the rename merges).
- **Must recover:** nothing automatically. Every failure stops visibly for the
  operator; the migration script is idempotent so a half-applied run re-runs.
- **Accepted failure:** a build session dying mid-run (recover from the work
  order and worktree); ledger staleness against the tracker (renderer marks
  it; manual sync); a missed nudge if the calibration store write is denied
  (reported in one line, never blocking).
- **Unsupported:** repos outside the spike's approved list; concurrent epics
  sharing one change directory; trackers other than GitHub issues.
- **Evidence owed:** validator, full suite, and post-install check green on
  the renamed tree; migration acceptance quantified over the approved list;
  the purge gate shown red before and green after each enumerated target; the
  renderer's completion gate against the pinned fixture; a finalize staging
  rows without prompting.
