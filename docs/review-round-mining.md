# Why reviews take eight rounds

Plan reviews in this flow converge in 8 to 9 rounds and code reviews in about 6. That is
not a property of hard changes. Roughly half the findings that consume a round are
generated by the review process itself, and every one of the six causes below has a
cheap structural fix.

## What we mined

20 Claude Code session transcripts across 4 repositories. About 14 of them contain real
review cycling (more than two rounds against the same artifact); the rest are single-pass
work kept as controls.

Every finding that consumed a round was classified. Approximate counts across the 14
cycling sessions:

| Finding class | Count |
| --- | --- |
| Real user-breaking bugs | 14 |
| Spec gaps and ambiguity | 35 |
| Speculative hardening and nits | 24 |
| Bugs introduced by a previous round's fix | 14 |
| Reviewer and process churn | 11 |

Reviewer and process churn covers unverified reviewer claims forwarded to the author,
re-litigation of settled decisions, and false negatives caused by the reviewer's own
stale test harness.

The two bottom rows, 25 of 98 findings, exist only because a review happened. Add the
speculative hardening row and roughly half of round-consuming findings are process
output rather than defects in the original work.

## Six root causes

### 1. Executable logic pinned as prose literals, never executed

The release-automation plan (PR 524, shared infrastructure library) pinned regexes, shell
fragments, and workflow conditions as markdown literals. It took 8 plan rounds. The
session's own summary: the cycle was "injecting roughly one defect per round while
removing several."

Every late-round blocker in that plan was an unspiked tool semantic: the release tool's
ignore-tags interplay, case-insensitivity in a workflow `startsWith` expression, and
shell operator precedence. A compiler or one table test settles each in seconds. Prose
review never settles them at all.

### 2. Fixes written from the finding text instead of the running code

Direct quote from a session: "round two's worst finding was caused by my fix, not by the
original code. I patched the sentence the finding named ... and wrote a new false
sentence twelve lines above one that already stated the exception correctly."

From another: "From round 3 onward every finding was in prose written in the immediately
preceding round."

The partial-fix variant is the same failure at smaller scale: a case-insensitivity fix
applied to 1 of the 3 regexes that shared its rationale, leaving 2 sites for the next
round to find.

### 3. One fact duplicated across many places bounds nothing

"Which titles release what" was encoded in 8 places. That is 28 pairs that can disagree
and nothing checking any of them. Each round samples different pairs, so the round count
is unbounded by construction.

The code-review skill's divergent-copies check exists because of this case. The
remaining gap is that the *fix* round does not re-run the check scoped to what the fix
touched, so a fix to one copy reliably mints a new disagreeing pair.

### 4. Reviewer objections forwarded unverified

A round-4 reviewer claimed the current pattern matched no real title. It was false. It
reached the writer, was baked into the plan as a task, and cost a full round to retract.

plan-review's objection-verification step (cycle step 3) closed this on the reviewer
side. There was no equivalent obligation on the fixer side in code-review.

### 5. Unbounded rubric plus a soft stop signal

Self-diagnosed in a meta session: the work-track review had no fixed rubric and stopped
on "round yields only wording polish." One review under that rule reached 11 rounds.

The two-axis code-review skill fixed the enumeration half of this. It shipped with no
hard round cap.

### 6. Facts carried from a prior ticket without regrounding

A secret count of 6 was carried from a prior ticket into its successor; the real count
was 8. The same session lost 3 rounds to an assumed decrypt failure mode on empty
strings that was never validated against the tool.

## The counter-example

The infra-plan-review build session generated real `pulumi preview --json` fixtures
against a throwaway stack *before* plan review. The review converged in one round, with
7 amendments all grounded in the empirical fixture, and needed zero code-review rounds.

Same reviewer, same rubric, same author. The difference is that the executable claims had
been executed before anyone reviewed prose about them.

## Two smaller patterns

* Cross-skill integration seams reviewed in isolation. persona-review was reviewed alone
  in round 1; all 4 round-2 blockers were about its wiring into plan-review's termination
  path.
* Reviewer false negatives sourced from the reviewer's own stale test harness, reported
  as defects in the change under review.

## What changed in the skills

**code-review** gained:

* A "Fixing findings" section: re-derive the fix from the code, not the finding text;
  update every copy of a fact a fix touches or collapse them to one authority; sweep the
  diff for every site the cited rationale covers; re-read the surrounding section after
  any prose edit.
* A re-review scope for divergent copies: enumerate the copies of each fact the fix
  touched and verdict each pair.
* A hard cap of three rounds, with a named structural diagnosis when round 3 still finds
  new violated items.
* A shared-brief line requiring executable literals to be executed against a real input.
* Integration contracts in the spec enumeration when a change wires into another
  component.

**plan-review** gained:

* The spike demand promoted to triage: pinned literals or asserted tool behavior draw
  the spike objection before the first cold pass reviews the prose.
* Inherited facts treated as unverified claims in the grounding axis.

## Proposed benchmark (not implemented)

Nothing below exists in `bench/` yet. It is a design, with no runnable arm and no
results.

* **Fixture.** A planted-defect change: one fact with 4 encodings, 2 of which disagree;
  one executable literal that is wrong in a way only execution reveals; one acceptance
  criterion partially met. Plus a scripted fix round that patches the named symptom only.
* **Arms.** The shipped skill versus the amended skill, same fixture, same model, n runs
  per arm.
* **Measures.** Rounds to converge, and count of defects introduced by fix rounds. The
  second is the one the amendments target; the first should follow.
* **Prediction.** Fix-introduced defects fall to near zero; rounds to converge fall from
  the observed 6 toward 3, bounded by the cap.
